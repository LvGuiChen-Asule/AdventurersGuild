# 23 性能设计

## WHY：MC 世界为什么不能"每 tick 扫一遍"？

MC 一个区块 16×16×384，实体/方块海量。如果任务系统每 tick 扫描所有实体、
所有玩家背包、所有任务目标，100 个玩家在线时就是灾难。

本项目性能设计的第一原则：**事件驱动，能不用定时器就不用定时器**。

## 事件驱动清单（V1.1 已实现）

| 行为 | 使用的 Forge 事件 | 处理成本 |
| --- | --- | --- |
| 进下界/末地 | PlayerChangedDimensionEvent | 一次 |
| 死亡 | LivingDeathEvent | 一次 |
| 击杀（HUNT/ELITE/BOSS） | LivingDeathEvent | 一次 |
| 拾取（COLLECT） | ItemPickupEvent | 一次 |
| 合成末影之眼 | ItemCraftedEvent | 一次 |
| NPC 互动（INTERACT） | PlayerInteractEvent.EntityInteract | 一次 |
| 龙攻击玩家 | LivingHurtEvent | 一次 |
| 凋灵生成 | EntityJoinLevelEvent | 一次 |
| 末地水晶破坏 | EntityLeaveLevelEvent | 一次 |
| 精英怪强化 | MobSpawnEvent.FinalizeSpawn | 生成时一次 |

## 少数"不得不定时"的检测（低频）

| 检测 | 频率 | 说明 |
| --- | --- | --- |
| EXPLORE 群系 | 每 5 秒（tickCount % 100） | 每秒一次改为低频，位置变化不敏感 |
| SURVIVE 存活计时 | 每 5 秒 | 计时精度足够 |
| TRANSPORT 送达 | 每 5 秒 | 位置判定 |
| 任务超时 | 每 5 秒 | 精度到分钟级足够 |
| 堡垒/要塞/外岛结构检测 | 每 5 秒 | 结构位置判定（只在对应维度） |

> 设计判断：任务目标里"位置/时长"类天然低频（5 秒粒度对玩家无感知），
> "拾取/击杀/合成"类高频精确事件全部走事件回调。

## 服务器权威与性能

1. **判定在服务端**：客户端不做任何进度判定，避免双端状态分叉；
2. **数据同步只发给变化的玩家**：不广播全服快照；
3. **实体不逐 tick 扫描**：精英怪只在生成事件时强化；NPC 日程是自带的 Goal AI；
4. **世界生成只做一次**：公会放置有 `guildGenerated` 标记，登录只是读坐标；
5. **NPC 每世界一次**：`npcsSpawned` 标记，杜绝重复生成刷实体。

## 网络同步（性能面）

- S2C 快照按玩家粒度下发（QuestManager/ChronicleManager 各自 sync）；
- 对话/档案/团队用独立小包，避免每次更新都带全量任务；
- 客户端只是显示层：收到包就刷新，不轮询服务端。

## 数据持久化（性能面）

- 玩家能力 NBT：随存档保存，字段版本化；
- GuildWorldData SavedData：只有 `setDirty()` 才写盘，不每 tick 保存；
- 每日板按"世界日"缓存：同一天不重抽，省去重复随机。

## 实测基线（V1.0 已测）

- 专用服务器冒烟：80 任务/22 池/3 链/3 商店/5 装备全部加载，`Done (7.435s)`；
- `gradlew build` PASS；
- 未做大规模多人压测（10 人以上）——已如实列入验证清单，不宣称支持。

## VALUE：体现什么策划能力？

- **性能预算意识**：先列"哪些必须定时、哪些必须事件"，再写功能；
- **规模化思维**：设计从单机即多人模型出发，避免"先能跑，多人就崩"；
- **诚实边界**：压测未做就写"未验证"，不把"应该没问题"当结论。
