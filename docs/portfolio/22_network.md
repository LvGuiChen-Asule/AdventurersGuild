# 22 网络与数据安全

## WHY：单人 Mod 为什么还要认真做网络？

MC 的存档在单机时也走"客户端-服务端"模型（内置服务器），
多人时更是完全分离。网络设计决定了：

- **防作弊**：玩家能不能直接改金币/任务？
- **一致性**：两个玩家看到的状态是否一致？
- **可扩展**：将来开放多人，现有设计要不要推翻重来？

本项目从一开始就按**服务器权威**设计，所以单机与多人走的是同一条链路。

## 服务器权威清单（已实现）

| 操作 | 客户端能做什么 | 服务端校验什么 |
| --- | --- | --- |
| 接任务 | 发 quest_id | 注册/存在/未重复/槽位/等级/声望/章节/前置/上板 |
| 完成发奖 | 无（不能请求完成） | 进度达标 → 移除任务 → 发奖一次 |
| 购买 | 发 shop+item | 商店存在/等级/金币/背包溢出掉落/非法退款 |
| 刷新 | 发请求 | 当日次数/费用递增/写入 SavedData |
| 对话 | 选分支 | 条件重新判定 + 动作服务端执行 |
| 金币/EXP | 无（无直写包） | 只有发奖路径可加，负数/超上限拒绝 |

## 防作弊与正确性（已实现）

1. **客户端无直写接口**：所有状态变更必须走 C2S 请求；
2. **奖励只发一次**：任务完成即从进行中移除，`COMPLETED` 守卫；
3. **非法输入拒绝**：未知任务 ID、未上板任务、负数/超大金币一律拒绝；
4. **金币上限**：1,000,000,000，防溢出；
5. **条件不信任客户端**：对话选项可用性由服务端重算（客户端传 index，服务端重算列表）；
6. **超时/下架**：服务端每秒检查时限与数据包重载后的任务存在性。

## 数据同步策略

- 快照只发给**状态变化的玩家**，不广播全服（性能 + 隐私）；
- 团队同步发给**全体在线成员**（PartyDataSync + GuildDataSync）；
- 世界事件写入 GuildWorldData，玩家事件写入 ChronicleState——两个维度各管各的；
- 客户端数据快照（ClientGuildData）在收到 S2C 后刷新当前界面，无需重连。

## 数据安全（存档层）

| 数据 | 存储 | 风险点 | 对策 |
| --- | --- | --- | --- |
| 玩家状态 | Capability NBT | 存档损坏/修改 | 字段版本化、死亡克隆保留、重置指令（OP2） |
| 每日板 | SavedData | 跨日刷新 | 按世界天数缓存，`lastRefreshDay` 防重复计费 |
| 世界事件/团队 | SavedData | 并发写 | 服务端单线程写，`setDirty()` 触发保存 |
| NPC | 实体 NBT | 重复生成 | `npcsSpawned` 世界标记 |

## IMPLEMENT：怎么落地？

- `network/GuildNetwork`：SimpleChannel 注册 + 协议版本校验（版本不符拒绝连接）；
- 每个包独立 encode/decode/handle；
- 服务端处理器全部走 QuestManager/PartyManager 等，不直接改数据；
- `OpenGuildScreenPacket` 由服务端决定打开哪个界面 → 客户端不能随意打开商店白嫖。

## VALUE：体现什么策划能力？

- **规则意识**：所有"边界"（门槛/次数/上限/防重复）先写成策划规则，再落代码；
- **反作弊思维**：理解"客户端不可信"，把校验收敛到服务端；
- **多人前瞻**：单机=内置服务器同链路，将来开服零改造；
- **文档能力**：12 包协议表可直接交给网络程序做联调。
